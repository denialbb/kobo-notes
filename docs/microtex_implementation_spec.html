Math Rendering

Design specification for LaTeX math in the KOReader Markdown Reader plugin — pure Lua now, native MicroTeX deferred

0. Status & history

An earlier revision of this document specified a native C++ MicroTeX integration (FFI wrapper, cross-compiled libmicrotex.so, SVG output). That integration was never implemented — no Makefile, no C/C++ source and no shared object ever existed in this repository or its history. Several of its technical claims were also wrong; they are corrected in §5 so the decision is not re-litigated later.

The decision now in force: implement math rendering in pure Lua, behind a swappable backend seam. This keeps DESIGN_final.md objective 3 intact — “achieve (1) and (2) without cross-compiling anything”. A native backend remains possible later, but is explicitly deferred.

1. Pipeline

Math is handled by bracketing the existing Markdown→HTML conversion described in DESIGN_final.md §5.4 / §6.3, not by replacing it.

Data flow:
.md source → interceptor: extract math → placeholder tokens → FileConverter:mdToHtml (vendored luamd) → substitute tokens → rendered HTML/image → write cache/md/<name>.html → ReaderUI:showReader → crengine

1 Extract before markdown conversion

Formula bodies are removed from the source and replaced with inert placeholder tokens before luamd ever sees the text. This is not an optimisation — it is required for correctness. LaTeX is dense in characters that Markdown treats as markup:

  • _ — subscripts (x_i) collide with Markdown emphasis, so a formula containing two subscripts silently becomes italic text with the underscores eaten.
  • * — collides with emphasis/strong the same way.
  • \ — every LaTeX command starts with a backslash, and Markdown treats backslash as an escape character, so \alpha can lose its backslash entirely.
  • Bracket and brace runs can be mistaken for link or reference syntax.

By the time luamd runs, the formula is gone and only an opaque token remains. The token must be chosen so that luamd passes it through unchanged and so that it cannot occur in real note text (a fixed prefix plus a counter and a nonce, containing no Markdown-significant characters).

2 Substitute after markdown conversion

Substitution happens on the generated HTML string, not on the Markdown. That ordering is what makes the backend seam possible: because the replacement is spliced into finished HTML, a backend is free to return either an <img> element pointing at a cached image file or a block of inline HTML (spans, tables, entities) that crengine lays out directly. Neither form would survive being fed back through the Markdown parser. It also means adding a new backend never requires touching the interception or conversion code.

Display math ($$…$$) substitutes into a block-level container; inline math ($…$) into an inline one. Whatever a backend returns is treated as HTML and therefore must be produced already escaped — escaping is the backend's responsibility, since only it knows whether its output is markup or text.

2. The backend seam

Three Lua modules, with the dependency arrow pointing one way only: the plugin depends on the facade, the facade depends on backends, backends depend on nothing in the plugin.

Module Role
math_renderer.lua Facade. The only module the rest of the plugin talks to. Selects a backend, owns the cache, owns the fallback policy. Its contract is “given LaTeX and a display/inline flag, return an HTML fragment” — it never returns an error to the caller, only a fragment (see §4).
math_backend_lua.lua Pure-Lua backend — ships now. No FFI, no native code, no build step. Handles the subset of LaTeX that actually appears in the notes; reports honest failure for anything outside that subset rather than emitting something wrong.
native backend Future, optional, deferred. Would implement the same backend contract over a native engine. Not present; see §5 for why.

A backend exposes exactly two things: a name, and a render function taking (latex, is_display) and returning either an HTML fragment or nil, err. Backend selection is a setting with a safe default; an unavailable or failing backend must degrade to the pure-Lua one, and a failing pure-Lua one degrades to source display. There is deliberately no backend init step in the contract that the caller must remember to run — a backend that needs setup does it lazily and reports unavailability through the same nil, err channel.

3. Caching

  • Content-addressed. The cache key is derived from the LaTeX content itself (plus the display/inline flag, the backend name, and a render version), not from the containing file, its path, or the formula's position. Identical formulas across different notes therefore share one cache entry, and editing a note only invalidates the formulas that actually changed.
  • Stored under KOReader's cache directory — alongside the generated HTML under cache/md/ in the KOReader data dir, reached via DataStorage. Not /tmp. On the Kobo, /tmp is volatile and cleared on reboot, which would force a full re-render of every formula after every power cycle; onboard storage persists. (An older revision used /tmp/microtex-cache/; deploy.sh still mops that up over SSH if configured, purely as legacy cleanup.)
  • The cache holds whatever the backend produced. A backend returning inline HTML may need no image files at all — the cache must not assume image output exists.
  • Because keys are content hashes, entries are never mutated, only added; a stale entry is impossible and eviction can be as crude as deleting the directory. deploy.sh clears it on every deploy so render tests start fresh.

4. Graceful degradation (a first-class rule)

Rule: a document must always open. Math rendering is an enhancement; a math failure of any kind — unsupported construct, malformed LaTeX, missing backend, cache write failure, unexpected Lua error — must degrade to showing the LaTeX source for that one formula and must never abort the conversion or prevent the note from opening.
  • Every backend call is wrapped so that an unexpected error is caught and turned into the same outcome as a clean failure.
  • The fallback is the original LaTeX source, escaped and marked up so it is visibly a formula the reader can still read and interpret manually. Silent deletion of the formula is the one unacceptable outcome.
  • Failures are logged for diagnosis but never surfaced as blocking dialogs while opening a document.
  • Degradation is per-formula. One unsupported formula must not disable math for the rest of the note.
  • This rule is what makes shipping a deliberately incomplete pure-Lua backend safe: partial LaTeX coverage produces readable source text, not breakage.

5. Deferred: native MicroTeX backend

Recorded here so the trade-off is not rediscovered from scratch. These are the real risks that led to deferral. Items marked UNVERIFIED were not empirically tested — they are read from documentation and source knowledge, and must be proven before any native work starts.

5.1 The upstream URL in the old spec was wrong

The old spec instructed adding https://github.com/X-Wei/microtex.git as a submodule. That is not the project. The maintained upstream is NanoMichael/MicroTeX. Any future work must start from the correct repository.

5.2 -DUSE_SVG=ON is not a real option

The old spec's CMake invocation passed -DUSE_SVG=ON. No such MicroTeX CMake option exists. CMake silently accepts unknown -D definitions, so this would have appeared to work and produced a build with no SVG support whatsoever. MicroTeX renders through an abstract Graphics2D interface; SVG output is not a build flag but a feature you implement, by writing a custom Graphics2D subclass that serialises draw calls to SVG. That is real work, not configuration. No build flags are asserted in this document; the correct ones must be read off the upstream CMakeLists.txt at the time the work is attempted.

5.3 SVG text rendering — RETRACTED, was overstated

An earlier revision of this document claimed crengine rasterises SVG via nanosvg, which renders paths only, and called this the single highest-risk item — formulas silently rasterising to blank boxes. That claim is wrong for the deployed device and is retracted.

Inspected directly on the mounted Kobo running KOReader v2026.07 (libs/libcrengine.so). There are no nanosvg symbols. The rasteriser is lunasvg:

_ZN7lunasvg8Document12loadFromDataEPKcjPNS_18external_context_tE
_ZNK7lunasvg8Document14renderToBitmapEjjj
_ZN22LunaSVGGlyphsCollector8addGlyphEv

lunasvg supports <text>, and the presence of LunaSVGGlyphsCollector::addGlyph together with the external_context_t parameter on loadFromData indicates crengine supplies its own font context to lunasvg for glyph rasterisation. A <text>-based SVG is therefore likely to render, and the glyph-outline-to-path work described below is probably not mandatory.

Still unverified: symbol inspection is not a render test. Which fonts resolve inside the SVG context, and whether MicroTeX's specific <text> output (with its font-family names and precise glyph positioning) survives, remain untested. The cheap experiment is unchanged and still worth doing first — render a hand-written SVG containing a <text> element inside a KOReader HTML document on device — but it is now a confirmation step, not a go/no-go gate. Note also that this finding is specific to v2026.07; older KOReader builds may differ.

5.4 It contradicts a project objective

A native backend requires an ARMhf cross-toolchain and a cross-compiled shared object, plus bundling .clm font data (MicroTeX's pre-processed glyph-metric format) inside the plugin directory. Both directly contradict DESIGN_final.md objective 3, “without cross-compiling anything — pure-Lua koplugins dropped into plugins/”, and both add per-device binary-compatibility risk that pure Lua does not have. The .clm files also add non-trivial size to a plugin that currently ships as a handful of text files.

5.5 Correction to the old API table

The old spec declared the initialiser as:

void microtex_init(const char* clm_font_path)

Returning void gives the Lua side no way to detect initialisation failure — no status code, no out-parameter, no error channel. Yet the same document's error-handling section claimed that a missing or invalid .clm font path “will fail early” and be handled. Those two statements are contradictory: with a void return, a failed init is indistinguishable from a successful one, and the first symptom would be a crash or silent blank output at render time. Its proposed mitigation — checking that the font file exists from Lua first — only catches a missing file, not a corrupt one, an unparseable one, or an engine that failed to initialise for any other reason.

Any future C-ABI wrapper must return a status the caller can test (and must catch C++ exceptions at the boundary, since letting them cross into LuaJIT is undefined behaviour). The signatures in the old table are not a specification and should not be treated as one; nothing in this document asserts a verified native API.

5.6 Deploy-time consequence

Because no native build exists, deploy.sh treats the native build as conditional: it builds only when a Makefile is present in the plugin directory, and otherwise prints a notice and continues. Previously it ran make clean unconditionally under set -eu, which failed immediately and aborted the entire deploy before the device was ever mounted.

6. What would reopen this decision

  1. The pure-Lua backend proving inadequate for formulas that actually occur in the notes — measured against real files, not hypotheticals.
  2. §5.3 being tested and resolved: proof that crengine renders glyphs from a given SVG form on the real device.
  3. An accepted answer to the cross-compilation objective in §5.4 — either the objective changes, or the artefact ships prebuilt and the toolchain stays out of the normal workflow.

Until all three hold, the pure-Lua backend is the implementation, and the seam in §2 is the only thing that needs to keep the option open.
